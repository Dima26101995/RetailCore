# Дорожная карта миграции RetailCore

## 1. Принципы

- Инкрементальная миграция: изменения по частям, с откатом.
- Не останавливать бизнес; нет окна на Big Bang.
- Не переписывать checkout, payment orchestration и core order create.
- Промежуточная ценность на каждом этапе.
- Все числовые пороги — параметры, которые должны быть согласованы; во входных данных их нет.

## 2. Этапы

### Этап 0. Подготовка и измерение

| Поле | Значение |
|---|---|
| Цель | Зафиксировать исходное состояние и границы изменений |
| Работы | Baseline метрик; инвентаризация Oracle-объектов; реестр партнёров и форматов; реестр потребителей staging; правила пилота |
| Промежуточное состояние | Baseline собран; известны владельцы данных и границы пилота |
| Зависимости | Доступ к логам, метрикам, схемам БД, командам |
| Метрики | Собраны baseline по checkout, статусам, интеграциям |
| Критерии готовности | Есть согласованный baseline; известны владельцы данных; определены границы пилота |
| Риски | Неполные данные; скрытые потребители |

### Этап 1 (T-01). Наблюдаемость и сквозная трассировка

| Поле | Значение |
|---|---|
| Цель | Сделать заказ прослеживаемым через монолит, .NET и Python |
| Работы | Ввести correlation id; покрыть точки входа и выхода; настроить трассировку и метрики |
| Промежуточное состояние | Заказ прослеживается end-to-end через монолит, .NET и Python |
| Зависимости | Этап 0 |
| Метрики | Доля заказов с полной трассировкой; время разбора инцидента |
| Критерии готовности | Ключевой сценарий прослеживается end-to-end; метрики доступны эксплуатации |
| Риски | Накладные расходы; старые участки без логирования |

### Этап 2 (T-02). Единый контур статусов и история заказа

| Поле | Значение |
|---|---|
| Цель | Дать единый источник истины по статусам и объяснимую историю |
| Работы | Согласовать модели статусов; выделить Order Status Service и Order Timeline; включить публикацию событий из монолита и batch; подключить поддержку |
| Промежуточное состояние | Статусы имеют единый источник истины; история доступна поддержке |
| Зависимости | Этап 1 |
| Метрики | Доля расхождений статусов; обращения по статусу; доля заказов с историей |
| Критерии готовности | Модели статусов согласованы с поддержкой, логистикой и аналитикой; история доступна поддержке; расхождения не выше согласованного порога |
| Риски | Неверный маппинг; двойная запись; ручные правки |

### Этап 3 (T-03). Интеграционный слой (ACL)

| Поле | Значение |
|---|---|
| Цель | Снизить дубли, задержки и ручной разбор партнёрских интеграций |
| Работы | Реестр партнёров; единые контракты; идемпотентность; retry; статус доставки; перевод части сценариев |
| Промежуточное состояние | Пилотные партнёры работают через ACL; дубли в пределах согласованного порога |
| Зависимости | Этап 1; этап 2 для статусов доставки |
| Метрики | Доля дублей; P95 подтверждения; доля ошибок интеграций |
| Критерии готовности | Пилотные партнёры работают через ACL; дубли не выше согласованного порога |
| Риски | ACL усложняется; партнёры не меняются; скрытые сценарии |

### Этап 4 (T-04, T-05). Канонические события и аналитический контур

| Поле | Значение |
|---|---|
| Цель | Дать единые цифры и снять нагрузку с операционной Oracle |
| Работы | Утвердить канонические события; назначить владельца модели; вынести тяжёлые чтения; перевести отчёты |
| Промежуточное состояние | Ключевые отчёты на каноническом слое; тяжёлые чтения вне операционной Oracle |
| Зависимости | Этап 2; этап 3 для событий доставки |
| Метрики | Доля отчётов на канонической модели; расхождения; P95 checkout; доля тяжёлых запросов |
| Критерии готовности | Ключевые отчёты используют канонический слой; тяжёлые чтения переведены; P95 checkout не хуже baseline |
| Риски | Свежесть данных; lineage; скрытые потребители |

### Этап 5 (T-06). Инвентаризация и изоляция Oracle-логики

| Поле | Значение |
|---|---|
| Цель | Подготовить основу для импортонезависимости |
| Работы | Реестр объектов и владельцев; изоляция некритичных процедур; план замены |
| Промежуточное состояние | Реестр Oracle-объектов согласован; некритичные изолированы |
| Зависимости | Этап 0; может идти параллельно |
| Метрики | Число инвентаризированных объектов; число изолированных некритичных |
| Критерии готовности | Реестр Oracle-объектов согласован с владельцами; некритичные объекты изолированы |
| Риски | Неполный перечень; критичная логика в процедурах |

## 3. Зависимости

```
Этап 0 ──► Этап 1 ──► Этап 2 ──► Этап 3 ──► Этап 4
   │
   └──────────────► Этап 5 (параллельно)
```

- Этап 1 нужен для проверки всех последующих.
- Этап 2 — основа для статусов доставки в ACL.
- Этап 3 — источник событий доставки для аналитики.
- Этап 5 не блокирует первые этапы, но нужен для импортонезависимости.

## 4. Риски и контроль

| Этап | Риск | Контроль | Условие остановки | Действие |
|---|---|---|---|---|
| 0 | Неполный baseline | Сверка источников | Baseline невозможно подтвердить | Остановить подготовку, уточнить источники |
| 1 | Неполная трассировка | Проверка ключевого сценария | Заказ не прослеживается | Остановить этап, вернуться к логированию |
| 2 | Расхождение статусов | Сверка старого и нового контура | Расхождение выше согласованного порога | Прекратить расширение, выполнить rollback |
| 2 | Двойная запись | Журнал и сверка | Потеря или дубль перехода | Прекратить расширение, выполнить rollback |
| 3 | Дубли у партнёров | Идемпотентность | Дубли выше согласованного порога | Остановить перевод партнёров, rollback |
| 3 | ACL усложняется | Ограничение ответственности | ACL начинает принимать бизнес-решения | Ограничить ACL, вынести бизнес-логику |
| 4 | Устаревание данных | Контроль свежести | Данные не соответствуют согласованной задержке | Остановить перевод отчётов, вернуть чтение |
| 5 | Пропущены потребители Oracle | Реестр потребителей | Найден критичный потребитель без владельца | Остановить изоляцию, уточнить реестр |

## 6. Критерии завершения программы первого этапа

- Checkout не деградировал относительно согласованного baseline.
- Статусы имеют единый источник истины и историю.
- Пилотные партнёры работают через ACL без роста дублей.
- Ключевые отчёты используют канонический слой.
- Тяжёлые чтения переведены в отдельный контур.
- Есть реестр Oracle-объектов и план дальнейшей изоляции.
- Все открытые пробелы (RTO/RPO, SLA/SLO, p95/p99, RPS/TPS, бюджет) закрыты или явно приняты как риск.
