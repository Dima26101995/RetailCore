# Точки трансформации и целевая архитектура первого этапа

## 1. Точки трансформации

### Основания выбора

Точки выбраны по трём критериям: значимость для бизнес-цели из кейса, техническая проблемность,
зафиксированная в AS-IS, и реализуемость в первом этапе с учётом ограничений.

| Точка | Основание |
|---|---|
| T-01 | Техлид: восстановление истории по заказу — почти ручная работа; трассировка не меняет бизнес-логику |
| T-02 | Техлид: статусы размазаны по сервису заказов, платёжному модулю и batch; чтение статусов меньше связано с транзакцией оформления |
| T-03 | Логистика: нет единого интеграционного контура; сначала стабилизировать слой интеграций, не трогая маршрутизацию целиком |
| T-04 | Аналитика: нет канонической модели; сначала выделить единый набор бизнес-событий заказа и доставки |
| T-05 | Аналитика: тяжёлые выгрузки попадают на операционную Oracle; вторым шагом убрать их из операционной базы |
| T-06 | Техлид: часть критичной логики в Oracle-процедурах; инвентаризация не меняет процедуры и идёт параллельно |

Не выбраны на первом этапе: замена монолита и Oracle, переписывание payment orchestration,
унификация каналов и всех партнёров — высокий риск или отсутствие промежуточной ценности.

### T-01 (шаг 1). Наблюдаемость и сквозная трассировка заказа

| Поле | Значение |
|---|---|
| Проблема AS-IS | На монолите логи есть, но цепочку по заказу собрать быстро не всегда удаётся; correlation id есть не везде; если заказ прошёл через монолит, .NET и Python, восстановление истории — почти ручная работа |
| Бизнес-влияние | Восстановление истории заказа требует ручной работы и участия команды |
| Почему участок подходит | Техлид предлагает начинать с того, что меньше связано с транзакцией оформления; трассировка не меняет бизнес-логику и контракты |
| Зависимости | Нет; выполняется первым |
| Ограничение | Не менять бизнес-логику |
| Изменение | Ввести correlation id и сквозную трассировку на участках оформления и обработки |
| Что не делаем | Не переписываем монолит и не меняем контракты партнёров |
| Метрика | Доля заказов с полной трассировкой; время разбора инцидента — значения не заданы |
| Риски | Накладные расходы; на монолите наблюдаемость хуже, часть старых участков может остаться вне трассировки |
| Следующий шаг | Инвентаризация точек входа и логирования |

### T-02 (шаг 2). Единый контур статусов и история заказа

| Поле | Значение |
|---|---|
| Проблема AS-IS | Часть переходов — в сервисе заказов, часть — в платёжном модуле, часть — в batch-процедурах; операторы поддержки вручную переводят заказ в технический статус; есть специальные статусы для маркетплейсов и партнёра |
| Бизнес-влияние | Без ручных вмешательств часть заказов зависала бы до утра; один и тот же заказ выглядит по-разному в разных витринах |
| Почему участок подходит | Техлид предлагает начинать с чтения статусов как участка, меньше связанного с транзакцией оформления |
| Зависимости | T-01: трассировка; события из монолита и batch |
| Ограничение | Монолит и внешние системы не меняются одномоментно |
| Изменение | Выделить сервис статусов и журнал переходов; монолит и batch публикуют события; поддержка видит историю и причину |
| Что не делаем | Не перестраиваем внутренние статусы Oracle и не меняем жизненный цикл целиком |
| Метрика | Доля заказов с расхождением статусов; обращения по статусу — значения не заданы |
| Риски | Неверный маппинг статусов; ручные правки; двойная запись |
| Следующий шаг | Согласовать пользовательскую и внутреннюю модели статусов |

### T-03 (шаг 3). Интеграционный слой (ACL) для партнёров

| Поле | Значение |
|---|---|
| Проблема AS-IS | Нет единого интеграционного контура: смесь REST, очередей, обмена через таблицы и периодических джоб; разная семантика доставки, дедупликация и идемпотентность решаются по-разному |
| Бизнес-влияние | Дубли заявок, задержки подтверждения, ручной разбор; клиент видит срок доставки, который потом меняется |
| Почему участок подходит | Логистика предлагает сначала стабилизировать слой интеграций, а не трогать маршрутизацию целиком |
| Зависимости | T-02: статус доставки |
| Ограничение | Партнёры не меняют свои API и форматы |
| Изменение | Ввести слой перевода и единые контракты: идемпотентность, retry, статус доставки |
| Что не делаем | Не унифицируем всех партнёров и не заменяем .NET-сервис целиком |
| Метрика | Доля дублей; P95 подтверждения; доля ошибок интеграций — значения не заданы |
| Риски | Недооценить исключения: крупногабарит, частичная поставка, split shipment, регионы, ручная переадресация, сбои API; ACL усложняется |
| Следующий шаг | Реестр партнёров, форматов и retry-правил |

### T-04 (шаг 4). Канонический слой событий заказа

| Поле | Значение |
|---|---|
| Проблема AS-IS | Формально канонической модели нет; есть несколько «почти канонических» представлений; один и тот же заказ выглядит по-разному в зависимости от источника и момента |
| Бизнес-влияние | Маркетинг, финансы и операционный блок называют разные цифры по выручке, отменам, возвратам и промо |
| Почему участок подходит | Аналитика предлагает сначала выделить единый набор бизнес-событий заказа и доставки, не перестраивая всю аналитику |
| Зависимости | T-02 и T-03: события заказа и доставки |
| Ограничение | В монолите нет одной чистой модели событий, которую можно сразу стримить |
| Изменение | Определить канонические события заказа и доставки; публиковать их из монолита и новых сервисов |
| Что не делаем | Не перестраиваем всю аналитику заново |
| Метрика | Доля отчётов на канонической модели; число расхождений — значения не заданы |
| Риски | Владелец модели не назначен; качество событий |
| Следующий шаг | Назначить владельца и утвердить схему событий |

### T-05 (шаг 5). Вынос аналитической нагрузки из операционной Oracle

| Поле | Значение |
|---|---|
| Проблема AS-IS | Часть отчётов идёт прямыми SQL в Oracle, часть — через staging, API, batch и CSV; тяжёлые отчёты и исторические выборки попадают на операционную Oracle |
| Бизнес-влияние | В пиковые окна операционная база «чувствует» аналитическую нагрузку; выгрузки уже просили ограничивать |
| Почему участок подходит | Аналитика называет вторым шагом убрать наиболее тяжёлые выгрузки из операционной базы |
| Зависимости | T-01: наблюдаемость; T-04: канонические данные |
| Ограничение | Свежесть данных и lineage должны быть понятны |
| Изменение | Выделить отдельный контур чтения (read replica / DWH) и перевести тяжёлые отчёты |
| Что не делаем | Не заменяем Oracle и не переносим все данные сразу |
| Метрика | P95 checkout; доля тяжёлых запросов к операционной БД — значения не заданы |
| Риски | Устаревание данных; скрытые потребители; lineage прослеживается только местами |
| Следующий шаг | Реестр отчётов и их требований к свежести |

### T-06 (параллельно). Инвентаризация и изоляция Oracle-логики

| Поле | Значение |
|---|---|
| Проблема AS-IS | Часть критичной логики живёт не в приложении, а в Oracle-процедурах и пакетах; при обсуждении выноса сервиса это часто не учитывается |
| Бизнес-влияние | Нельзя безопасно двигаться к импортонезависимости, пока не понятно, что завязано на Oracle |
| Почему участок подходит | Инвентаризация не меняет процедуры и может идти параллельно остальным шагам |
| Зависимости | Не блокирует первый этап; идёт параллельно |
| Ограничение | Нельзя менять критичные процедуры без понимания потребителей |
| Изменение | Реестр Oracle-объектов, владельцев и потребителей; постепенная изоляция некритичных |
| Что не делаем | Не заменяем Oracle на первом этапе |
| Метрика | Число инвентаризированных объектов; число изолированных некритичных — значения не заданы |
| Риски | Неполный перечень; скрытые batch-потребители |
| Следующий шаг | Инвентаризация с командой ИТ |

## 2. Целевая архитектура первого этапа

### Цель первого этапа

Проверяемый шаг, а не финальная архитектура: единая картина заказа и статусов, сквозная
трассировка, контролируемые интеграции с партнёрами и аналитика вне операционной Oracle при
сохранении монолита и Oracle.

### Границы

- Входит: статусы, история, наблюдаемость, ACL, канонические события, аналитический контур.
- Не входит: замена монолита, замена Oracle, переписывание checkout и payment orchestration,
  унификация каналов и всех партнёров.

### Основной сценарий

1. Клиент оформляет заказ в канале.
2. Checkout вызывает Pricing и Processing.
3. Processing создаёт заказ, резерв, платёжную сессию и выбирает доставку.
4. Монолит публикует события заказа в Event Bus.
5. Order Status Service формирует статус, Order Timeline — историю.
6. ACL передаёт заявку партнёру и публикует события доставки.
7. Analytics Data Platform читает события и Oracle, отдаёт отчёты.
8. Поддержка видит историю; Admin корректирует статус.

### Исключения

- Повторная оплата, частичная отмена, split shipment, возвраты.
- Недоступность партнёра или платёжного провайдера.
- Расхождение статусов, ручной разбор, зависший заказ.

### Компоненты

**Остаются в монолите:**

- Checkout / Order API;
- Pricing & Promo Logic (включая Promo Service);
- Order Processing;
- Payment Orchestration;
- Delivery Routing;
- core order create.

**Изолируются:**

- партнёрские интеграции — через Integration Gateway (ACL);
- аналитика — через Analytics Data Platform, отдельно от операционной Oracle;
- статусы и история — через Order Status Service и Order Timeline.

**Выносятся первыми:**

- T-01: наблюдаемость и сквозная трассировка;
- T-02: единый контур статусов и история заказа.

**Появляются:**

| Компонент | Ответственность |
|---|---|
| Order Status Service | Единая модель статусов и переходов |
| Order Timeline | История изменений и причины отклонений |
| Integration Gateway (ACL) | Единые контракты, идемпотентность, retry |
| Event Bus | Публикация канонических событий заказа и доставки |
| Analytics Data Platform | Отдельный контур чтения и витрины |
| Observability | Correlation id, трассировка, метрики |

**Сохраняются без изменений:**

- Oracle как операционная БД и источник части логики;
- .NET-сервис для существующих партнёрских сценариев;
- Python-пайплайны до постепенного перевода;
- Admin / Support tools до замены на новый интерфейс истории;
- Async / batch exchange — до перевода на Event Bus.

### Данные и состояния

- Заказ, текущий статус, история переходов, канонические события, платёжная сессия, заявка
  партнёру.
- Хранилище статусов и событий — новое; конкретная технология не зафиксирована.
- Oracle остаётся источником заказов, резервов и части логики.

### Интеграции

- Каналы и маркетплейсы → Checkout: заказы и обновления.
- Монолит → Oracle: заказ, резерв, служебные таблицы.
- Payment Orchestration → платёжный провайдер: платёжная сессия.
- Delivery Routing → ACL: заявка на доставку.
- Монолит → Event Bus: события заказа и статусов.
- Event Bus → Order Status Service и Analytics Data Platform.
- ACL → Event Bus: события доставки.
- ACL → службы доставки: заявки и подтверждения.
- Order Status Service → Order Timeline: переходы.
- Order Timeline → поддержка: история заказа.
- Analytics Data Platform → Oracle: чтение для витрин.
- Analytics Data Platform → BI: отчёты.
- .NET → ACL: существующие партнёрские сценарии.
- .NET → Oracle: staging до перевода.
- Python → Analytics Data Platform: аналитические выгрузки.
- Admin → Order Status Service: корректировка.
- Поддержка → Admin: ручной разбор.
- Observability → Event Bus и Order Status Service: метрики и трассировка.

### Метрики

Метрики — в паспортах точек T-01…T-06. Целевые значения не заданы, уточняются у бизнеса,
эксплуатации, поддержки и аналитики.

### Ограничения

- Не останавливать бизнес.
- Oracle остаётся; часть логики в процедурах.
- Партнёры не меняют контракты.
- On-prem, ограниченная виртуализация.
- Бюджет, сроки, RTO/RPO, SLA/SLO, p95/p99, RPS/TPS не заданы.

### Почему допустимо с точки зрения риска

- Checkout, payment orchestration и core order create не переписываются.
- Новые компоненты работают вокруг монолита и получают события, а не управляют ядром.
- Статусы и история включаются через события, с периодом сосуществования и сверкой.
- Партнёры подключаются через ACL, их API не меняются.
- Аналитика читает из отдельного контура, не из операционной Oracle.
- Расширение — поэтапное, с пилотом и rollback.

### Что опасно трогать на первом этапе

- Checkout и core order create — критичный контур оформления.
- Payment Orchestration — внешние платёжные сценарии.
- Oracle-процедуры — часть критичной логики.
- Контракты партнёров — внешние обязательства.
- Жизненный цикл статусов целиком — высокий риск расхождений.
