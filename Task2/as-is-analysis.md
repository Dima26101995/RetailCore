# Анализ текущего состояния RetailCore (AS-IS)

## 1. Цель и метод

Зафиксировать, как платформа устроена фактически: участники, границы, потоки данных, интеграции,
зависимости и проблемные зоны. Основа — три стенограммы интервью с разработчиками и фрагмент
кода. Исходная `AS-IS.puml` из кейса используется как ориентир, а не эталон. Результат —
`as-is.puml` и `as-is.png`.

Метод: три измерения AS-IS — потоки данных, интеграции, зависимости. Дополнительно — проверка
артефактов и фиксация пробелов.

## 2. Анализ артефактов

| Артефакт | Что дал | Ограничение |
|---|---|---|
| `interview-1-tech-lead.md` | Устройство монолита, Oracle-логика, связность, fallback, длинные транзакции | Взгляд одной роли |

Основой стали три стенограммы разработчиков и фрагмент кода. Они дали фактическое поведение
системы, локальные обходные решения, технические ограничения и скрытые зависимости.

## 3. Контекст AS-IS

**Акторы:** клиент, оператор поддержки, бизнес-пользователи.

**Внешние системы:** маркетплейсы, платёжные провайдеры, службы доставки, внутренние BI/отчёты.

**Внутри RetailCore:**

- каналы: интернет-магазин и мобильные каналы;
- Java-монолит: Checkout / Order API, Order Processing, Pricing & Promo Logic, Status Management,
  Payment Orchestration, Delivery Routing;
- Oracle: операционная БД, справочники, часть бизнес-логики, staging/shared tables;
- вспомогательные сервисы: .NET integration service, Python analytics jobs;
- Async / batch exchange: очереди, задания, выгрузки;
- Admin / Support tools: ручные проверки и корректировки.

## 4. Потоки данных

| Шаг | Процесс | Вход | Выход | Хранилище |
|---|---|---|---|---|
| 1 | Приём заказа | Данные заказа из канала | Заказ, начальный статус | Oracle |
| 2 | Расчёт цены и промо | Заказ, правила, промокод | Итоговая сумма, скидка | Oracle, конфиги, код |
| 3 | Выбор доставки | Регион, тип доставки, канал, правила | Маршрут, партнёр | Oracle, конфиги |
| 4 | Резервирование и оплата | Заказ, сумма, способ оплаты | Резерв, платёжная сессия | Oracle, внешние системы |
| 5 | Передача в логистику | Заказ, маршрут, партнёр | Заявка партнёру, статус доставки | Очереди, staging, внешние системы |
| 6 | Управление статусами | События оплаты, доставки, ручные действия | Новый статус, история | Oracle, сервис заказов, batch |
| 7 | Аналитика | Заказы, статусы, платежи, логистика | Витрины, отчёты | Oracle, staging, CSV |
| 8 | Поддержка | Обращение, карточка заказа | Комментарий, флаг, повторная проверка | Admin tools, Oracle |

**Ключевой разрыв:** статус заказа формируется в нескольких местах, поэтому один и тот же заказ
может выглядеть по-разному для клиента, поддержки, логистики и аналитики.

## 6. Карта зависимостей

### Жёсткие зависимости

- Checkout зависит от Oracle, Pricing, Payment Orchestration и Delivery Routing.
- Оплата зависит от внешнего платёжного провайдера.
- Доставка зависит от внешних служб и их подтверждений.
- Ручной разбор зависит от Admin tools и возможности менять технический статус.

### Мягкие зависимости

- Уведомления можно повторить.
- Аналитика и BI могут работать с задержкой.
- Часть batch-выгрузок не блокирует заказ.

### Красные зоны

| Зона | Почему рискованна |
|---|---|
| Oracle в центре checkout | Длинные транзакции, общая БД, часть логики в процедурах |
| Общая БД и staging-таблицы | Скрытая связность, изменение схемы ломает потребителей |
| Статусы в нескольких местах | Расхождения, ручные правки, batch-корректировки |
| Синхронные вызовы оплаты и доставки | Задержка внешней системы останавливает оформление |
| Отсутствие сквозной трассировки | Заказ нельзя восстановить через монолит, .NET и Python |
| Fallback промо | Поведение отличается от целевого, бизнес не знает масштаба |

## 8. Что не подтверждено

- Точные схемы потоков данных и актуальная документация — отсутствуют.
- Полный перечень Oracle-объектов и их владельцев — не предоставлен.
- Перечень всех потребителей staging-таблиц — не предоставлен.
- Значения RTO/RPO, SLA/SLO, p95/p99, RPS/TPS — отсутствуют.
- Правила деградации при отказе оплаты, логистики, Oracle — не заданы.
- Требования к консистентности статусов и аналитики — не заданы.
- Требования PCI DSS и 152-ФЗ — не сформулированы.
- SLA внешних партнёров — не зафиксированы.

## 9. Выводы

1. AS-IS — монолит с общей Oracle-базой и набором разнородных интеграций; границы ответственности
   размыты, часть логики находится в БД.
2. Главные ограничения для изменений — связность, общая БД, фрагментированные статусы и
   отсутствие канонической модели данных.
3. Наиболее рискованные зоны — checkout, оплата, доставка и Oracle.
4. Первый этап не должен переписывать ядро; изменения нужно строить вокруг него.
5. Количественные требования отсутствуют — это архитектурно значимые пробелы, а не основание
   придумывать значения.
